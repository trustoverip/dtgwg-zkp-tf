With the specification repository open, the task force's work lives in three repositories. The relationship between them is worth stating once, because the rule that holds them apart is the same rule the constructions themselves are held to.

| repository | what it holds | who acts there | what leaves it |
|---|---|---|---|
| `trustoverip/dtgwg-zkp-tf` | the requirements (v0.4), the drafting rules, these discussions, the working board thread (#18), the note on how members and their assistants work the evidence | the task force: positions, decisions, ratification | decisions and requests — a request becomes a construction record |
| `trustoverip/dtgwg-zkp-spec` | the specification: construction records, the requests they answer, public-input conventions, proving-system entries, considerations, conformance — and the `conformance/` apparatus that validates the records and checks the generated text against them in CI | editors, by pull request, under DCO | the rendered specification; record ids other specifications may cite by `[[xref]]` |
| `github.com/mitchuski/dtgwg-zkp-mage` | the evidence: reference runtimes with measured costs, conformance fixtures, the verification registry of independent reproductions, the board where records are written and advanced, the generator that renders records into specification text | constructors, runners, the registry maintainer | data — records, fixtures, registry row ids — and never a dependency |

**The path a claim takes.** A discussion here yields a request. A constructor writes the record on the board and, when there is one, a runtime with measured cost. A different party rebuilds it on independent hardware and files a run; the registry re-derives the verdict and publishes a row. The record's state rises — `requested → carded → constructed → run → vetted → published` — and the specification text is regenerated from it. The pull request that carries the change to the specification repository fails its own CI if the text and the record disagree. Nothing in the specification says more than a record shows; no record says more than a runtime measured; no runtime says more than a stranger reproduced.

**What crosses, and what does not.** Records, fixtures and row identifiers cross. Dependency does not: the specification cites the evidence repository and never imports from it, so a specification never depends on one laboratory and a laboratory is never mistaken for a specification. Decisions stay here; the specification records them and the evidence repository tests them.

**The ZK Book edition.** The evidence repository renders the same records into the same chapters — requests answered, cryptographic background, public inputs, construction records, proving systems, considerations, conformance — as one volume that reads front to back, and keeps beside it what a specification cannot carry: the board with each record's state and history, the drafts of these posts and the rite that gates them, a watch over the upstream threads that feed the records, the run notes, and the chronicles of how the work moved. That edition is called the ZK Book. The name says what the deliverable is built as: not a survey of proof systems but a book of constructions, each page of which can be checked — the record it renders from, the validator that admits it, the row that vets it. The background chapters draw on the agentprivacy body of work, cited once at the bottom as the root of understanding they came from; the narrative that work carries stays there, and only the explanation travels.

Reading the specification is reading the book with the working removed. Reading the book is reading the specification with the working shown. Both are generated from the same records, and the records are what a reviewer should argue with.
