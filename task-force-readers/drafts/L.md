The catalog's manifest is at version 1 with fourteen entries: ten Longfellow libzk v1 circuits (ISO mDL and EUDI PID document types, one to four attributes, content-addressed, about 300 KB each) and four Microsoft vega-prover keys (P-256 mDL, revision 11 deprecated, revision 12 active). Its entry schema — id, system, systemVersion, docTypes, artifact hash and size, source origin, toolchain, licence, openSource, publishedAt — maps one-to-one onto the proving-system entries the ZKP specification draft carries. The catalog appears there as an as-signed entry: substrate for the legacy-rails route, proving over credentials exactly as already issued, and kept visibly apart from constructions over issuer-chosen commitments so the two are never compared as if they answered the same question.

The pilot proposed on 25 August is now concrete: run entry `longfellow-libzk-v1_8_1_4259_2945` through the registry's acceptance flow — fetch by sha256, rebuild from `source.origin` at the pinned commit with the stated toolchain, compare digests. Whether the artifact rebuilds is the finding either way. If it does, a `reproduction` field on catalog entries and a `catalogEntry` field on registry rows are the two small JSON changes that make the halves one table.

Whether a reproduction field on entries would be welcome is a question for the SIROS team; the acceptance flow is public and the first run can be filed from either side.
